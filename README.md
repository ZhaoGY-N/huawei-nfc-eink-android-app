# Huawei NFC E-Ink Android App

Android 墨水屏刷新工具，当前版本 **v2.17.0**。默认通过 Shizuku（Shell / Root），也可手动选择进程兼容、旧版 Root 直连，或前台 App 通信＋Root HAL 实验路径，调用兼容系统的 NXP Q-Poll，再通过 Android ISO-DEP 向 **552×768 四色华为 A0 / A1 / A0X 墨水屏**传图刷新，使用板内已存驱动。

## 功能

- 设备：授权连接、屏幕类型、首次使用清单，以及折叠的芯片检测、仅供能、Q-Poll 能力测试、普通 NFC-A 对照和只读检查。
- 发送：独立展示最终像素预览、发送确认、进度和结果；发送进度条、充能与等待计时仅显示在此页面。失败时原始错误信息和错误码直接展示，无需先打开日志。
- 编辑：独立预览与“构图 / 色彩 / 更多”工具，支持选图、最近图片、测试图、裁切、旋转、亮度 / 色温 / 对比度、二值化、阈值、色块简化和抖动。与发送页共用同一份准备好的像素快照，保留全屏缩放与 1:1 像素查看；切换到发送页不自动发送。
- 设置：折叠的发送参数、执行方式与兼容实验、屏幕校色。参数保存在本地；校色支持相册照片四色取样及 RGB / 十六进制手调。
- 本地自动保存编辑草稿，包括原图、当前裁切结果、裁切窗口、旋转和显示方式；进入校色测试后可退出并恢复原编辑。
- 保留屏幕规格和原厂扫描配置检查，不限制屏幕 UID；发送前确认，运行中可停止。
- D1 的 C0（FMSC APPID）接受参考实现支持的 `201EA001` 和 `00000001`；未知值仍停止，其他屏幕规格校验保留。

## 使用

1. 首次进入“设备”页，开启 NFC，并在 Shizuku 中启动服务、允许授权连接。已有授权会自动复用；Root 服务需由 Magisk / KernelSU 允许 Shizuku 的 Root 权限。兼容执行方式位于“设置 → 执行方式与兼容实验”；旧版 Root 直连在执行时请求本 App 的 Root 授权，无需启动 Shizuku。
2. 在设备页按实物选择 A0 / A1 / A0X，核对屏幕来源及原厂驱动。D1 无法自动识别实体类型。需要诊断时展开“检测工具”；检查与寻卡不会自动启动传图。
3. 点击“完成设置，前往发送”。以后打开默认进入发送页，自动恢复上次编辑草稿。需要调整时切换到独立的“编辑”页：通过“构图”选图、旋转和裁切，“色彩”调整整体效果，“更多”设置二值化、阈值、简化和抖动。完成后点击“完成编辑 · 去发送”或底部“发送”，不会自动开始传图。
4. NFC、连接、屏幕类型或预览未准备好时，页面显示原因与处理入口。全部就绪后点击“发送到墨水屏”，核对图片与参数并确认。授权连接恢复后不会自动继续发送。
5. 持续贴合并保持应用在前台，直到发送页显示结果。传输百分比只表示图像传输；充能或上电计时结束不代表实屏刷新完成。失败时发送页直接显示原始错误，包括屏幕 `SW`、控制器状态、异常名称或后端退出码（以实际返回为准），并保留排查建议和日志入口。

仅适用于兼容 Q-Poll 的手机系统及相同原厂配置的目标屏；不能仅凭接口存在或型号名称判定兼容。刷新结果取决于实际供能与屏幕状态。中断可能留下不完整画面，程序不会自动重发刷新指令。

## 前台 App 通信与 NXP HAL 扩展（v2.17.0）

2026-10-25 修复版：版本名称保留 2.17.0，内部 versionCode / Shizuku 服务版本更新为 33。驻留的用户服务以前只在构造时保存 APK 路径，覆盖安装后会继续向 worker 传入已删除的旧路径，触发 `ClassNotFoundException: QPollWorker`，本机 ART 表现为退出码 134。现改为每次操作重新向系统查询当前安装包路径，并检查 UID、文件可读性与 `classes.dex`；两种驻留后端都采用此规则，进程入口继续使用传入的 APK 快照。保留新排版，MainActivity 仅更新两处服务版本号。

本次 K90 Pro Max（25102RKBEC / SN220U）实测：相同 APK 只重启旧用户服务，默认组合即恢复 D1 和完整刷新，用户确认实物完整；修复版前台 App＋Root HAL 完成 D1、上传、D4、忙→连续三次空闲和恢复；同一修复 APK 再次覆盖安装后，原用户服务 PID 不变，自动出现 `APK_REFRESH` 并正常启动 worker。2.16.1 与修复版的 HAL 固定进程入口均通过 D1；直接 Q-Poll 在两版均未通过普通寻卡命令及响应确认，测试后已用本机 `cmd nfc disable-nfc / enable-nfc` 恢复。一次未收到标签不作为机型不支持的结论，以上均不扩大为所有 ROM / 组合的兼容承诺。

本版界面进一步分为“发送 / 编辑 / 设备 / 设置”：最终预览、发送操作和进度集中在发送页，编辑页有独立预览和全部调整工具；发送进度不占用其他页面。设备检测保留本页文字结果与停止入口。最近图片改为两列大缩略图，点击图片或紧凑的“选用”按钮即可恢复图片，时间与删除操作分开显示；缩略图解码尺寸同步提高并限制内存占用。失败面板直接显示完整原始错误信息，后续进程退出或恢复失败不会覆盖先前已返回的错误码。

- 原有三种执行方式、三个寻卡选项的位置和内部标识不变；默认仍为 Shizuku 用户服务＋系统 QTag。原执行方式的 NFC worker、四／五参数 ReaderMode、直接 Q-Poll 与屏幕协议继续保留。
- 所有 HAL 路径统一接受 SN220 / SN220U / SN100U 固件配置；仍要求 Root、arm64 和实际 HAL / 符号匹配。新增 `/odm/etc/libnfc-nci.conf`、`/vendor/etc/libnfc-nci.conf` 作为固件配置读取来源，原配置路径优先级不变。配置准入不代表完成机型适配，未知配置仍由 Root 执行时检查。native 源码和两个原生资产均未修改。
- 设置 → 执行方式与兼容实验新增“前台 App 通信＋Root HAL（实验）”。只有选中后才显示 Root 管理通道：Shizuku Root 用户服务、Shizuku Root 进程兼容、直接 Root 管理 HAL。最后一项不需要 Shizuku，也不会以 UID 0 调用 ReaderMode；前台路径始终由普通 App UID 通信。
- 前台 Q-Poll 固定使用 NXP HAL，不扩展为 QTag / 直接 Q-Poll 组合。App 使用公开 `enableReaderMode(NFC_A | SKIP_NDEF_CHECK)` 收 Tag，复用原 `PanelSession`、图像快照、D1 / 单次 PIN / D3 / D4 / 忙闲判断和连接前的有限重新寻卡。普通 NFC-A 对照只取得会话锁，不注入 HAL；仅供能仍不执行屏幕 APDU。检查芯片操作不注入或寻卡。
- Root HAL 管理采用独立服务和入口，不修改原 ShellBridge 的任务协议；两条路径共用会话锁及 worker 锁。Binder 死亡、管道关闭、心跳超时和总时限均使新会话进入关闭状态，晚到的心跳不能重新开启。切出前台时请求先关闭 HAL 改写，再释放 ReaderMode 与会话锁；停止会中止连接，不重放已经开始的 APDU。
- 关闭 HAL 改写无需等待外部统计进程；清理任一步失败仍继续执行后续释放，并报告恢复未确认。Root 库按原设计驻留到 HAL 进程重启，关闭的是会话改写开关，不宣称已卸载库。Shizuku 用户服务版本同步更新，以免升级后沿用旧的型号检查代码。

验证：完整 Java 回归、APK 编译与 v2 / v3 签名检查通过；新增测试覆盖 SN100U 准入、原 SN220 / SN220U 条件、Root / arm64 限制、未知与其他芯片拒绝、配置读取、心跳超时、关闭状态不可逆、清理顺序及失败后的继续释放。原协议及图像基线的 12 个导出文件逐字节一致。最初发布时仅离线验证；内部版本 33 已在上述 K90 Pro Max 上覆盖安装并完成本节记录的对照。SN100U 本机验证仍缺少实体设备，新路径继续标记实验。

## 兼容整合与旧版 Root 对照（v2.15.0）

基于本地 v2.14.0 基线提交 `0e03e13`，保留图像调整、相册校色、自动连接、充能计时和最长五分钟的仅供能模式。

执行方式与寻卡方式独立选择，默认仍为 **Shizuku 用户服务 + 系统 QTag**。执行方式保存，下次打开沿用；寻卡实验方式不保存，每次打开回到系统 QTag。运行中不能切换，不会因失败自动更换后端、重新认证或重发图像/D4。

| 执行方式 | 实际身份与适用场景 |
|---|---|
| Shizuku 用户服务（当前模式，默认） | 保留现有 UserService；Shizuku Shell 直接执行，Shizuku Root 准备底层后经 `su 2000 + runcon` 切换到 Shell 通信，身份切换失败即停止 |
| Shizuku 进程兼容 | 通过服务端 `newProcess()` 启动固定入口，绕开 Android 16 上的 UserService/LoadedApk 启动异常；Shizuku Shell/Root 的后续 worker 身份规则与当前模式相同 |
| Root 直连（旧版） | 恢复 `su -c app_process` 路线，worker 以 **UID 0** 调用 NFC，不强制切换为 Shell；无需 Shizuku，也不会在当前模式失败时偷偷启用。部分 ROM 的 ReaderMode 不接受 UID 0，失败后应手动换回当前模式 |

进程兼容/Root 直连通过有长度限制的 stdin 管道传递固定任务与图像，继承 Android 环境变量，不依赖外部存储权限或公共任务目录。每秒发送存活信号，停止、管道关闭或五秒收不到信号会请求结束本轮；三种执行方式共享会话锁、worker 锁和恢复处理，禁止并发寻卡。实际身份、SELinux 域和所选方式写入日志。

- **ReaderMode 四/五参数**：运行前先解析五参数签名，不存在时选择四参数；启动、重新寻卡、退出复用同一个方法。已有方法调用失败时不再尝试另一签名。只解决接口签名差异，不代表目标机已完整刷屏。
- **A0X**：参考并感谢 [PR #9 / luzamm](https://github.com/ZhaoGY-N/huawei-nfc-eink-android-app/pull/9)，在 A0 行交错前交换左右半幅，预览执行逆变换；原 A0/A1 输出保持不变。仅适用于半屏顺序相反，不作为半宽压缩或任意镜像的通用修复。
- **SN220 HAL 兼容**：需 Root 和匹配的 HAL，保留现有会话内注入、关闭改写再恢复普通寻卡的顺序。可在旧版 Root 直连中手动选择，但这一个组合尚未真机验证，不宣称所有 SN220/ROM 可用。
- **直接 Q-Poll（实验）**：从 reader-test 分支整合，必须手动选择。保留 ReaderMode 回调，确认普通寻卡后发送 RF_DEACTIVATE 和 `0x71` RF_DISCOVER，核对真实 NCI 命令与响应；退出检查普通寻卡恢复。缺少 HAL 日志、控制器拒绝或恢复未确认均报错，不自动降级重放。仍未确认 RMX3888 等目标手机的完整刷屏。
- 不加入第三方 NFC 固件/HAL 移植模块，不刷写手机 NFC 固件或屏幕 DB/DA。默认单次 PIN 和 D4 约束保留。

验证：Java 回归覆盖三种屏幕布局的独立全帧映射、实际 D3 数据和预览、原有协议/图像/仅供能/取消行为、Root/Shell 身份隔离、四/五参数选择、直接 Q-Poll 响应/恢复以及管道任务长度和存活信号。APK 编译和 v2/v3 签名验证通过。新执行选项、目标 ROM 的 Root 授权、Binder 进程管道、NFC 恢复和实体刷新仍待真机验证；本次没有安装或刷新实体屏。

## NFC 仅供能（v2.14.0）

## 屏幕校色（v2.12.0）

1. 在“设置 → 屏幕校色”点击“显示校色测试图”，再到“刷图”确认发送。测试图左上黑、右上白、左下黄、右下红，直接使用固定四色编码，绕过校色、二值化、抖动、简化和裁切。可退出校色测试恢复原编辑，也可选择新图片退出基准图模式。

3. 在照片中依次点选黑、白、黄、红色块中心并确认每种颜色，可拖动取样框或重新选择颜色重取。取样框覆盖照片短边约 2% 的区域，在解码为 sRGB 的图片上按线性光平均；避开边缘、反光和阴影。全部四色确认后点击“保存并启用校色”；取消不改写配置，也不替换当前编辑图片。

校色模式将输入映射到取样黑白范围，在统一的线性 RGB 空间内进行加权距离量化、蛇形 Floyd–Steinberg 误差扩散；图像简化也使用该色板并在线性光下平均。纯黑白端点与中性灰受到保护。黑白二值化保留原阈值逻辑；预览按最终发送编码解码，再以校色色板显示，属于近似实物预览。

无标准色卡时，结果包含相机与光源偏色，适合相对优化；没有建立绝对色度校准或复杂 LUT。相册照片在本机临时解码，只有四色数值和启用状态保存到设置。

离线验证覆盖取样平均、边界和无效色板、黑白范围归一化、中性灰与纯黑白保护、各简化档位、A0 / A1 打包后校色预览，以及现有图像/协议回归。APK 构建与签名检查通过；相册选择器、取样操作与实物显示效果仍待手机验证。

## 构建与验证

需要 Python 3.9+、JDK 17、Android SDK platform android-34、build-tools 34.0.0，以及 Android NDK（本次验证使用 27.2.12479018）。设置 `JAVA_HOME`、`ANDROID_HOME`、`ANDROID_NDK_HOME` 指向本机安装目录，然后在仓库根目录运行：

```sh
python3 tests/run_java.py
cc -std=c11 -O1 -g -Wall -Wextra -Werror -fsanitize=address,undefined tests/nci_rewrite_test.c -o build/nci-rewrite-test
build/nci-rewrite-test
cc -std=c11 -O1 -g -Wall -Wextra -Werror -fsanitize=address,undefined tests/hal_discovery_test.c -o build/hal-discovery-test
build/hal-discovery-test
cc -std=c11 -O1 -g -Wall -Wextra -Werror -fsanitize=address,undefined tests/hook_debug_test.c -o build/hook-debug-test
build/hook-debug-test
python3 build.py
```

脚本使用 Android SDK 的命令行工具构建，无 Gradle、无构建期下载。Shizuku API / provider / aidl / shared 13.1.5 依赖已固定在 `libs/`。构建脚本当前使用 Unix 工具路径；Windows 可在 WSL 中运行。

设置 `ANDROID_NDK_HOME` 后，`build.py` 自动运行 `native/build.sh`，从源码生成 arm64 兼容库及注入器。生成物位于忽略的 `assets/native/`，不采用 fork 的预编译二进制。也可先单独运行 `sh native/build.sh`；后续构建会校验源码与二进制清单，拒绝缺失或过期的原生资产。

如安装了 `lzokay==2.1.0`，可独立检查解压与扫描打包：

```sh
python3 tests/check_fixtures.py build/<protocol-tests-directory>
```

APK 和 SHA-256 输出在 `dist/`。首次构建会在 `build/` 生成本地调试签名密钥；密钥、构建缓存和 APK 不纳入 Git。自行构建时需要保留自己的密钥，以支持后续覆盖安装。

```sh
adb install -r dist/QPollLab-2.17.0.apk
```

## v2.11-root-test4 HAL 库名正则匹配

- 共享 `native/hal_name.h` 中的 POSIX 扩展正则 `^nfc_nci([._-][[:alnum:]]+)*\.so$`，对完整文件名匹配；注入器的 maps 扫描和兼容库的 `dl_iterate_phdr` 使用同一实现。覆盖点号、下划线或连字符分隔的厂商、芯片族与版本后缀，不枚举两个库名。
- 可匹配 `nfc_nci.nqx.default.hw.so`、`nfc_nci_nxp_snxxx_v2.so`、其他版本后缀及 `nfc_nci.so`；拒绝相似前缀、`.so.bak`、`(deleted)` 和无关的 `libnfc_vendor_extn.so` / 固件库。
- maps 同一路径的多个段按一个库处理；一个进程存在多个不同匹配库，或多个进程符合条件时拒绝注入。hook 在任何 GOT 写入前遍历完整模块列表，同样拒绝多个候选，防止选中首个同名族模块。
- 库名匹配只负责筛选候选，仍要求两个目标函数存在、类型正确、GOT 原始地址一致，且两个方向安装确认成功。未验证函数 ABI 的变种仍不能宣称兼容。
- 用户手机的实际库 `/odm/lib64/nfc_nci_nxp_snxxx_v2.so` 已只读提取到忽略的 build 目录核对；两个目标函数和 JUMP_SLOT 重定位项均存在。此版本完成离线匹配回归、静态分析及 APK 构建；尚未在手机注入测试。

## v2.11-root-test5 注入发送路径与统计

- 用户 test4 实测已确认 HAL 正则匹配及 GOT 安装成功，但两次注入寻卡超时；原系统 QTag 路径随后立即收到 Tag。三轮均使用 Shizuku UID 0 / worker UID 2000，因此区别在于寻卡后端，不能归因于 Root 身份切换。
- 对实际 HAL 离线反汇编发现 `phNxpNciHal_write_unlocked(unsigned short, const uint8_t *, int)` 的独立调用路径。除原 `write_internal` 外，新增该 GOT 入口（若存在）；严格保留第三个参数，两层仅改写 NFC-A `00`，已是 `71` 时不重复改写。仍要求至少一条发送路径及接收路径安装确认。
- 新增导出的固定版本统计结构。`--status` 只读 `/proc/<pid>/mem`，不 ptrace、不加载库、不远程调用、不改写 HAL。服务在 worker 启动前与恢复普通寻卡前各读取一次累计值。
- `HOOK_SLOTS` 显示实际安装的入口数及旧版升级数；`HOOK_STATS` 显示两条 TX 路径的调用、发现与改写次数，以及 RX/发现响应次数；`HOOK_GATE` 显示开关检查状态、原始 syscall 返回值、属主、权限和时间差；`HOOK_PACKET` 仅记录发现命令、控制器应答与发现/激活通知的前后最多 32 字节。不会记录 APDU、PIN 或图像。
- HAL 回调仅使用内联原子操作、固定大小采样和 raw syscall；不在回调内写日志文件、调用动态加载器或阻塞等待采样锁。状态为累计值，需对比两个 phase。
- 恢复顺序调整：worker 请求恢复，Root 服务先读取统计、删除兼容开关并确认，再由 worker 释放 ReaderMode；避免普通 NFC 恢复命令仍被转换成 Q-Poll。确认缺失超过 20 秒明确报告恢复未确认。
- 更新兼容库时，只允许替换位于本应用固定目录、64 位十六进制内容哈希命名、Root 所有且无组/其他写权限的既有 hook。直接连接 HAL 原函数，不串联旧版；旧库不卸载，避免仍在执行的回调失效，失败时回滚到之前的 GOT 值。其他来源的 hook 继续拒绝。
- 离线测试覆盖双 TX 入口的计数/改写、gate-off 直通、重复改写抑制、RX 归一化、控制器响应采样、APDU 排除、非阻塞采样及本应用旧库路径约束。仍需用户手动测试实际寻卡和恢复握手。

## v2.11-root-test7 连续选图裁切修复

修正裁切确认时的状态顺序：弹窗的 dismiss 回调可能晚于预览刷新调用，此时 `editingCrop` 仍为 true，导致刷新被跳过。首次裁切时，“留白→填满”的选项变化可能再次触发刷新；加载下一张图片后，选项已是“填满”，因此不会有这次补偿刷新，预览和发送快照可能仍是裁切前的图片。
